# 记忆教训总结

> 生成时间：2026-09-04
>
> 目的：把历史记忆里的踩坑、纠偏和稳定偏好整理成一份可直接阅读的 Markdown。它不是新的项目事实来源，而是一份协作和工程判断护栏。

---

## 1. 总原则

记忆的作用不是替代当前源码、当前日志、当前测量值和用户最新指令。

记忆的作用是提醒我：以前在哪些地方容易跑偏，下一次遇到相似场景时，先把边界守住，再做判断。

优先级应当是：

```text
用户最新指令
当前文件 / 当前源码 / 当前差异
当前构建输出 / 当前串口输出 / 当前板上测量
用户已经确认的结论
历史记忆
通用经验
```

因此，所有记忆都应该带着一个前提使用：

```text
记忆是护栏，不是证据本身。
证据要从当前现场重新拿。
```

## 2. 协作边界教训

### 2.1 不要扩大用户的明确范围

历史教训：用户给了具体路径、具体值、具体范围、具体旧到新方案时，不能把它当成“只是一个起点”，然后擅自扩展到更多文件、更多模块、更多重构。

以后应该这样做：

1. 先执行用户明确说出的范围。
2. 范围外内容只作为风险提示或后续建议。
3. 如果必须扩大范围，先说明原因并等待用户确认。

判断句：

```text
用户说了哪一个文件，就先只看/改哪一个文件。
用户说了哪一个现象，就先围绕这个现象找证据。
用户说了 old -> new，就按这个迁移方向做，不另起路线。
```

### 2.2 问题不是默认的编辑命令

历史教训：用户问一个事实问题时，不能自动升级成改代码、改配置、写测试、提交或推送。

以后应该这样做：

1. 用户问“是不是”“为什么”“在哪里”时，先回答事实。
2. 用户没有明确要求修改时，不声称“已修复”。
3. 如果发现明显修法，可以写成“建议改法”，但不要直接越权动手。

特别是在文档分析、原因分析、架构解释里，要区分：

```text
解释问题
提出方案
实际修改
构建验证
提交推送
```

这五件事不能混成一件事。

### 2.3 遇到歧义先定对象

历史教训：对象不明确时，如果我强行猜多个方向，就容易把讨论带偏。

以后应该这样做：

1. 如果用户说的“这个”“那里”“那个项目”不清楚，先确认对象。
2. 如果用户明确说“不是 X”，马上停止 X 路线。
3. 不要用旧记忆覆盖用户当前纠正。

### 2.4 不要顺手做额外工程动作

历史教训：无关注释、无关文件、额外测试、额外重构、提交、推送、PR 都不能顺手做。

以后应该这样做：

1. 文档任务只写文档。
2. 代码任务只改必要代码。
3. 上传、提交、推送、开 PR 都必须用户明确要求。
4. 如果工作区已有脏改动，默认视为用户或其他流程的工作，不擅自回滚。

## 3. 文档写作教训

### 3.1 文档要写成真实主题，不要只模仿结构

历史教训：之前有文档重写时，容易匹配参考文档的章节形式，却没有把用户真正关心的主体讲透。

以后写架构文档时，优先回答：

1. 这篇文档真正要讲的对象是谁。
2. 它在工作区里的身份是什么。
3. 上下级关系是什么。
4. 代码设计机制是什么。
5. 当前源码证据在哪里。

对于 `zephyr_user`，主线应该是：

```text
zephyr_user 是公共子树 / 维护者工作区
projects/<user> 是用户区 / 产品工程
framework 是公共能力层
boards、thread、prj.conf、Kconfig、CMake 是业务装配边界
```

### 3.2 长度要求是硬边界

历史教训：用户说“4000-5000 行够了”时，这就是硬约束，不应该继续为了“更完整”而无限扩写。

以后应该这样做：

1. 先满足目标长度。
2. 不用重复段落堆体量。
3. 若内容超出范围，先删重复比较，再补关键证据。
4. 结束前检查标题、代码块、陈旧路径和目标长度。

### 3.3 架构文档必须锚定当前源码

历史教训：文档如果继承旧结构或旧路径，容易留下已经过时的目录、符号和结论。

以后写这类文档时，要先查当前源码和构建链，再写判断。

在 `zephyr_user` 里，常见证据链是：

```text
project/CMakeLists.txt
project/Kconfig
project/thread/CMakeLists.txt
board / DeviceTree / overlay
framework/zephyr/module.yml
framework/init/*
framework/cmd/linker/*
Kconfig 选择
CMake 装配
DTS 生成
链接段注册
启动阶段遍历
线程运行
```

## 4. zephyr_user 工程边界教训

### 4.1 不要混淆两个 drivers

历史教训：`zephyr_user/drivers/` 和 `framework/drivers/` 名字都叫 drivers，但职责不同。

以后必须区分：

```text
zephyr_user/drivers/
  子树级 Zephyr-module 风格底层驱动层。

framework/drivers/
  架构层 C++ 硬件访问封装层。
```

这两个层次一旦混淆，后面的 CMake、Kconfig、接口归属和可移植边界都会乱。

### 4.2 framework 六模块是核心词汇

当前稳定词汇是：

```text
algorithm
cmd
drivers
init
modules
topic
```

用户区也可以有自己的平行六模块层，再加上 `project/`。因此判断一个功能放哪里时，要先问：

```text
这是公共框架能力，还是用户项目能力？
这是底层适配，还是硬件访问封装？
这是算法，还是模块，还是 topic 数据契约？
这是调试控制面，还是业务线程？
```

### 4.3 主干和用户区职责要分清

`zephyr_user` 更像父级公共子树和维护者工作区。

普通产品项目更像子级用户区，主要保留自己的：

```text
boards/
thread/
prj.conf
Kconfig
CMakeLists.txt
业务配置
```

公共能力沉淀在父级，业务闭环留在用户区。这样才能让框架可复用、项目可迁移、维护关系清楚。

## 5. 构建与装配教训

### 5.1 application-mode 优先接入 app

历史教训：有些代码通过 `zephyr_library()` 能编译，但没有真正链接进应用，导致“看起来构建了，实际 app 用不到”。

以后在应用模式模块里，优先考虑：

```cmake
target_sources(app PRIVATE ...)
target_include_directories(app PRIVATE ...)
```

除非当前仓库已经明确使用 `zephyr_library()` 并且目标确实需要独立库，否则不要随手切换装配模型。

### 5.2 Kconfig 要走既有链路

历史教训：随手改根 `Kconfig` 容易破坏已有的项目/线程/功能选择链。

以后新增功能开关时，要先看：

```text
project Kconfig
thread Kconfig
framework Kconfig
module.yml
select / depends on 链
```

自有内部符号可以用 no-prompt bool 管理，但用户可见开关应该进入既有层级。

### 5.3 外部模块路径要加 EXISTS 保护

历史教训：可选外部模块路径如果无条件加入 `ZEPHYR_EXTRA_MODULES`，在其他机器、其他用户区或 CI 上可能直接炸。

以后凡是 optional path，都应先判断：

```cmake
if(EXISTS "...")
  list(APPEND ZEPHYR_EXTRA_MODULES "...")
endif()
```

## 6. HPM 与 CI 教训

### 6.1 低层 HPM 修改必须补丁化

历史教训：如果直接改官方 `zephyr`、`sdk_env`、`sdk_glue`、`cherryusb`，本机能跑，但 CI 或其他 checkout 无法复现。

以后低层修改要同步维护：

```text
E:\Zephyr_HPMicro\sdk_glue_user\zephyr-patches\
apply-patches.sh
源代码改动
生成补丁
修改理由
CI 可复现路径
```

也就是说，底层修复不能只是“我本机改过了”，必须变成别人能重新应用的补丁。

### 6.2 上传前检查 HPM 用户树

历史教训：主仓库 CI 会单独检查 HPM 相关树，如果 `sdk_glue_user` 有未推送或未对齐内容，主仓库上传后可能失败。

以后涉及 HPM 上传/推送前，先检查：

```powershell
git -C E:/Zephyr_HPMicro/sdk_glue_user status
```

主仓库、HPM 树、补丁目录、CI 期待状态必须对齐。

## 7. 硬件调试教训

### 7.1 源码证据和板上证据要分开

历史教训：板级问题不能只靠源码猜，也不能只盯着一条 warning。应该把证据分层。

以后硬件/USB/板卡 bring-up 要分成：

```text
源码证据
文档证据
DTS / overlay / binding 证据
原理图证据
构建输出证据
串口日志证据
寄存器状态证据
板上电压 / 波形测量证据
```

当板上测量和厂商文档或 DTS 假设冲突时，优先相信板上测量。

### 7.2 不要过早发明栈原因

历史教训：USB 或板卡 bring-up 中，如果太早把问题归因到协议栈，会错过更直接的主失败路径。

以后应该先隔离主失败路径：

```text
是否上电
时钟是否有效
PHY 是否出复位
角色是否正确
VBUS/attach 是否成立
控制器是否 start
中断是否出现
EP0/SETUP 是否出现
主机侧是否真的收到数据
显示工具是否只是没换行/没刷新
```

先拿证据，再命名原因。

### 7.3 用户已经测过的点不要重复推回去

历史教训：HPM5361 USB0 调试里，用户已经测过 MCU 封装管脚 DP/DM，却还把问题推回连接器、串联电阻或 ESD 路径，这是明显绕回旧路。

以后如果用户已经给出测量结果：

```text
把测量结果当作新的起点。
不要让用户重复做已排除路径。
只有出现新反证时才重开旧假设。
```

## 8. UART 调试教训

### 8.1 用户确认的根因就是当前工作真相

历史教训：用户已经确认根因或排除了路径后，继续反复怀疑 timing、console 干扰、线程抢占等旧理论，会浪费时间，也会显得不尊重现场证据。

以后应该这样做：

1. 用户确认的结论先作为工作真相。
2. 旧猜测只能保留为“曾经猜过但未证实”。
3. 没有新证据时，不重新争论已排除路径。

### 8.2 用户指定端口或动作时，先做原动作

历史教训：用户说 `uart3` 或“先加日志”时，不能切到别的串口，也不能换一套诊断计划。

以后应该：

```text
指定 uart3，就看 uart3。
指定加日志，就先加日志。
指定最小改动，就不顺手扩成结构调整。
```

### 8.3 串口显示问题要区分发送、接收和工具缓冲

历史教训：UART 曾经出现过 PC 侧没加换行导致行为异常，也出现过 TX 字节可能被宿主显示工具延后刷新。

以后分析 UART 时，要明确区分：

```text
MCU 是否真的发了
UART 驱动是否回调完成
PC 是否真的收到了
串口工具是否显示/刷新/换行
协议是否以换行作为触发条件
```

## 9. USB 快速验证教训

### 9.1 “把官方例子复制到这里”就是最小实验

历史教训：用户只是想临时验证 USB，结果被扩成 helper 目录、额外 CMake wiring 和结构化封装，这会偏离“快速验证”的本意。

以后遇到这类请求，默认选择：

```text
直接改当前 test 文件
尽量少改 CMake
先验证现象
验证完再讨论是否抽象
```

在相关 tflm 场景里，优先检查用户当前指定的 test 文件，而不是先设计新目录。

## 10. IMU / Parser / PC 脚本教训

### 10.1 当前生产者输出才是契约

历史教训：parser 或 adapter 如果根据旧脚本、旧记忆、相似模块猜 marker，就很容易和当前固件输出错位。

以后修改 parser 前必须先看：

```text
当前 producer 源码
当前串口原始输出
当前事件名
当前字段名
当前前缀
当前状态值
真实 sample line
```

记忆只能提醒“这里以前错过”，不能代替当前 producer。

### 10.2 marker 必须逐字匹配

历史教训：IMU 识别脚本不能把 `open_ident_start`、`closed_ident_start`、`ident_start` 混用。

以后必须按当前固件实际输出：

```text
open-loop  -> open_ident_start
closed-loop -> closed_ident_start
```

不能因为名字像、模式像、旧脚本写过，就替换 marker。

### 10.3 PC 脚本不能静默等待

历史教训：脚本没有输出时，用户无法判断它是在等 marker、没收到数据、解析失败、进度未到，还是串口错误。

以后 PC 侧 capture/parser/tuning/identification 脚本必须持续显示：

```text
当前阶段
是否收到原始数据
解析是否成功
当前进度
剩余目标
阻塞条件
完成状态
中断状态
串口错误
```

脚本可以等待，但不能像死了一样等待。

## 11. 注释和编辑风格教训

### 11.1 IMU 相关注释优先中文

历史教训：在 IMU 相关文件里，擅自改成英文注释会和用户偏好冲突。

以后在 `modules/imu/*` 相关代码里：

1. 优先中文注释。
2. 短注释优先用 `//`，能同一行就同一行。
3. 文件头、函数、结构体等较长说明保留仓库已有 Doxygen 风格。
4. 不把“短注释用 //”扩大成“所有块注释都改成 //”。

### 11.2 改现有文件时 patch in place

历史教训：删除文件再重建会制造无意义 diff，也容易误伤用户已有改动。

以后编辑现有文件时：

```text
直接在原文件 patch
保留周围风格
只改必要范围
不做格式化大清洗
```

## 12. 文档型请求教训

### 12.1 分析文档就是文档任务

历史教训：用户要问题分析文档时，不能顺手改源码、配置或脚本。

以后如果请求是：

```text
写分析文档
写问题分析
整理 Markdown
总结方案
```

默认只改 `doc/` 下的 Markdown。即使发现明显代码修法，也先写成“建议修改”，等待用户明确授权再动代码。

### 12.2 如果误碰了源文件，要只回滚自己的误改

历史教训：工作区可能有用户已有改动，不能为了撤销自己的错误而把别人的修改也回掉。

以后如果误改了不该动的源文件：

```text
只撤销自己刚刚造成的那部分
说明碰了哪个文件
继续完成原来的文档任务
```

## 13. 记忆使用教训

### 13.1 记忆不能覆盖当前事实

有些记忆是历史偏好，有些是旧结论，有些只是某次事故后的纠偏。它们的可靠性不一样。

以后使用记忆时要先判断：

```text
这是稳定协作偏好吗？
这是当前仓库结构事实吗？
这是某次硬件测量事实吗？
这是旧版本源码事实吗？
这是需要重新验证的运行期事实吗？
```

低漂移的协作规则可以直接作为护栏；高漂移的源码、构建、日志、硬件状态必须重新验证。

### 13.2 严重错误才值得写入记忆

历史教训：不是所有临时观察都适合写进记忆。轻量、一次性、无复用价值的信息会污染判断。

以后只有满足这些条件时才值得记忆：

```text
错误严重
容易重复
影响协作信任
影响工程边界
会导致明显时间浪费
以后遇到相似任务能避免踩坑
```

## 14. 最终戒律版

可以把这些记忆压缩成下面几条：

1. 用户最新指令优先，明确范围不可擅自扩大。
2. 问题不是编辑命令，文档不是代码授权。
3. 当前源码、当前输出、当前测量值优先于历史记忆。
4. 用户确认的根因和排除路径，在没有新证据前就是工作真相。
5. `zephyr_user` 文档必须围绕公共子树、用户区、framework、构建链和生命周期讲清楚。
6. application-mode 构建优先确认代码是否真正进了 `app`。
7. HPM 底层修改必须补丁化，否则 CI 和其他 checkout 不能复现。
8. 硬件 bring-up 要分清源码证据、日志证据和板上测量证据，测量值优先。
9. parser 以当前 producer 的真实输出为契约，marker 和字段不能猜。
10. PC 脚本等待时必须持续显示状态，不能静默。
11. 注释、文档和代码风格跟随仓库现状，不做无关清洗。
12. 记忆是防跑偏护栏，不是替代现场调查的答案库。
