# 轮腿机器人当前状态与节点职责

> 更新时间：2026-09-27  
> 本文描述当前源码和 `sim.launch.py` 配置的系统，不把规划文档中的后续功能算作已实现功能。

## 1. 一句话说明

当前机器人已经是一个由 `chassis` 统一控制六个执行器的轮腿平衡系统：

- 两个轮电机负责前后平衡、行驶和偏航；
- 左右髋、膝四个电机同时承担俯仰共模、身高和横滚差模控制；
- Pitch 使用 8 状态、3 输入 LQR；
- Roll 使用 4 状态、2 输入 LQR；
- 不同身高使用多工作点增益调度；
- 六路力矩经过统一限幅、变化率限制、软限位和安全监督后才发给 Gazebo。

但是它目前仍然是**平地局部平衡控制器**，没有地形感知、碰撞识别和自动越障状态机。Roll 能阻止左右腿自由分离，却不会在碰到障碍时自动缩腿或抬腿。

## 2. 物理机器人是什么

模型名为 `wheel_leg_robot`，包含：

- 一个 `base_link` 底盘；
- 左右各一条两连杆腿；
- 两个髋关节；
- 两个膝关节；
- 两个驱动轮关节；
- 底盘 IMU；
- 模型级关节状态发布器。

六个受控运动关节依次是：

1. `left_wheel_joint`
2. `right_wheel_joint`
3. `left_hip_joint`
4. `right_hip_joint`
5. `left_knee_joint`
6. `right_knee_joint`

标准姿态下，髋轴到轮轴的竖直距离约为 `0.072 m`。轮半径为 `0.030 m`，两根腿杆长度均为 `0.056 m`。

模型定义：`project/robot/models/bodys/wheel_leg_robot.xacro`。

## 3. 正常仿真的运行结构

执行：

```bash
ros2 launch project sim.launch.py
```

会形成下面的数据链路：

```text
                                      /imu
Gazebo 物理与传感器 ── ros_gz_bridge ─────────────┐
       │                                          │
       └──────── /joint_states ───────────────────┤
                                                  ▼
键盘节点（单独运行） ─ /chassis/cmd_vel ──> chassis
                                                  │
                                   六路关节目标力矩│ /motor/*/command
                                                  ▼
                                      六个 MotorNode
                                                  │
                                      /motor/*/cmd_force
                                                  ▼
                                      ros_gz_bridge
                                                  │
                                                  ▼
                                         Gazebo 六个关节
```

正常 launch 中还会启动 `robot_state_publisher`，并由一次性的 `ros_gz_sim create` 把机器人生成到 Gazebo 世界里。

## 4. 正常运行的节点

### 4.1 `chassis`：整车控制核心

进程入口：`project/node/chassis/chassis.cpp`  
主要实现：`project/node/chassis/chassis.hpp`

订阅：

| 话题 | 类型 | 用途 |
|---|---|---|
| `/imu` | `sensor_msgs/msg/Imu` | 读取 roll、pitch 和三轴角速度 |
| `/joint_states` | `sensor_msgs/msg/JointState` | 读取两轮和四个腿关节的位置、速度 |
| `/chassis/cmd_vel` | `geometry_msgs/msg/Twist` | 前后、偏航和离散身高指令 |

发布六路力矩目标：

| 话题 | 执行器 |
|---|---|
| `/motor/left/command` | 左轮 |
| `/motor/right/command` | 右轮 |
| `/motor/left_hip/command` | 左髋 |
| `/motor/right_hip/command` | 右髋 |
| `/motor/left_knee/command` | 左膝 |
| `/motor/right_knee/command` | 右膝 |

控制周期为 `0.001 s`，即目标 1 kHz。这个节点完成以下工作。

#### Pitch/前后/腿共模 LQR

Pitch 控制器的状态为：

```text
X_pitch = [s, s_dot, pitch, pitch_rate,
           q_h_common, q_h_common_rate,
           q_k_common, q_k_common_rate]
```

输入为：

```text
U_pitch = [tau_w_common, tau_h_common, tau_k_common]
```

控制律为：

```text
U = U0 - K * (X - Xref)
```

它同时负责：

- 车身俯仰平衡；
- 前后速度与位移参考；
- 两条腿的共同髋角、膝角；
- 共同身高；
- 髋膝静态重力前馈。

#### Roll/左右腿差模 LQR

Roll 控制器的实际反馈状态为：

```text
X_roll = [q_h_diff, q_h_diff_rate,
          q_k_diff, q_k_diff_rate]
```

输入为：

```text
U_roll = [tau_h_diff, tau_k_diff]
```

这里的差模定义为左右关节差的一半：

```text
q_diff = (q_left - q_right) / 2
```

Roll 模型假设两轮都与地面接触，此时车身 roll 可由左右腿几何差唯一确定。因此：

- IMU 的 `roll`、`roll_rate` 不直接进入 4 状态 Roll LQR；
- IMU roll 用于倒地保护和“腿几何预测 roll 与真实 roll 是否一致”的诊断；
- 髋、膝差模才是 Roll LQR 的闭环状态。

Roll 的作用是限制左右腿分离、抑制侧向发散。它不会主动改变两条腿的共同身高。

#### 偏航外环

偏航没有进入 Pitch 或 Roll LQR。`chassis` 使用 IMU 的 `yaw_rate` 做一个比例外环，把结果变成左右轮差动力矩。

```text
tau_w_diff = yaw_kp * (yaw_rate_target - yaw_rate)
```

它控制“转多快”，目前不控制绝对航向角。

#### 身高控制与增益调度

`target_height_m` 是髋轴到轮轴的目标竖直距离。

- 键盘 `=`：目标高度增加 `1 mm`；
- 键盘 `-`：目标高度减少 `1 mm`；
- `height_rate_mps` 将高度变化限制为平滑斜坡；
- 运动学模块把高度换算成髋、膝共模目标；
- 根据当前指令高度，在相邻工作点之间插值 `K`、`X0`、`U0` 和 `roll_per_q`。

当前加载六个高度工作点：

```text
0.058 m、约 0.072 m、0.080 m、0.090 m、0.100 m、0.104 m
```

增益文件位于 `project/gains/wheel_leg/`。

启动时，`chassis` 会严格校验：

- Pitch 状态顺序和输入顺序；
- Roll 状态顺序和输入顺序；
- 控制周期 `dt`；
- 轮半径；
- 当前展开 URDF 的模型哈希；
- `K/X0/U0` 的维度与有限性。

任意一项不匹配都会拒绝启动，防止旧增益驱动新模型。

#### 六路力矩统一分配

控制器先得到共模与差模力矩，再恢复左右执行器：

```text
tau_left  = tau_common + tau_diff
tau_right = tau_common - tau_diff
```

腿部采用“Pitch 共模优先、Roll 差模使用剩余余量”的策略。统一分配器随后执行：

1. 共模/差模恢复；
2. 单执行器力矩限制；
3. 左右成组缩放；
4. 力矩变化率限制；
5. 髋膝软限位恢复力矩；
6. 输出裁剪诊断。

当前主要上限：

- 轮平衡共模：`0.20 N·m`；
- 轮偏航差模：最大 `0.08 N·m`；
- 每个髋、膝关节：`1.5 N·m`；
- 腿关节速度护栏：`6 rad/s`。

#### 安全监督

`chassis` 会检查：

- IMU 是否到达以及是否超时；
- `/joint_states` 是否包含全部六个关节以及是否超时；
- 状态是否包含 NaN/Inf；
- 控制回调是否严重超期；
- `|pitch|` 或 `|roll|` 是否超过倒地阈值；
- 任一髋膝是否越过硬限位。

进入安全状态后会立即把六路力矩清零。故障恢复后，需要持续健康一段时间，再重置位移原点、动态状态和力矩分配器，然后重新交还 LQR，避免安全逻辑在临界点反复抢控制权。

### 4.2 六个 `MotorNode`：执行器适配与最后一道护栏

进程入口：`project/node/motor/motor.cpp`  
通用实现：`ros2_layer/node/motor/motor.hpp`

一个 `motor` 进程内运行六个 ROS 节点：

| 节点名 | 负责关节 |
|---|---|
| `/motor_left` | 左轮 |
| `/motor_right` | 右轮 |
| `/motor_left_hip` | 左髋 |
| `/motor_right_hip` | 右髋 |
| `/motor_left_knee` | 左膝 |
| `/motor_right_knee` | 右膝 |

每个节点只负责一个关节：

1. 订阅自己的 `/motor/<name>/command`；
2. 从 `/joint_states` 取自己的速度反馈；
3. 交给通用 `modules::motor::Motor`；
4. 做最终力矩限幅和命令超时保护；
5. 发布 `/motor/<name>/cmd_force`；
6. 由桥接把该力矩送进 Gazebo 的 `ApplyJointForce`。

当前六路全部工作在 `effort` 模式。不能在平衡 LQR 和执行器之间再套速度 PI，否则多出的积分和延迟会与平衡环互相对抗。

若超过 `0.05 s` 没收到新力矩命令，电机节点会独立输出零力矩。因此即使 `chassis` 卡死，执行器侧仍有超时兜底。

### 4.3 `ros_gz_bridge`：ROS 2 与 Gazebo 之间的桥

由 `sim.launch.py` 启动，负责：

- 六路 `/motor/*/cmd_force`：ROS 2 → Gazebo；
- `/joint_states`：Gazebo → ROS 2；
- `/imu`：Gazebo → ROS 2；
- `/clock`：Gazebo → ROS 2。

它不计算控制量，只转换消息并完成 Gazebo 关节力矩话题的重映射。

### 4.4 `robot_state_publisher`：发布机器人坐标树

它读取展开后的 `robot_description`，发布 URDF 对应的 TF 结构，供可视化和其他 ROS 节点使用。

它不参与物理仿真，也不输出电机力矩。

### 4.5 Gazebo 与生成机器人进程

Gazebo 负责：

- 刚体和关节动力学；
- 地面、梯形障碍和碰撞；
- 关节力矩执行；
- IMU 和关节编码器仿真。

`ros_gz_sim create` 是一次性生成器：从 `/robot_description` 创建 `wheel_leg_robot`，生成完成后不承担持续控制职责。

## 5. 需要单独运行或已经退出主链的节点

### 5.1 `keyboard`：人工遥控，默认不随 launch 启动

入口：`project/node/keyboard/keyboard.cpp`  
实现：`ros2_layer/node/keyboard/keyboard.hpp`

运行方式：

```bash
ros2 run project keyboard
```

必须在有 TTY 的前台终端运行。它只发布 `/chassis/cmd_vel`：

- 方向键：前后和左右转向；
- `=`：发送一拍 `linear.z = +1`，要求长高一步；
- `-`：发送一拍 `linear.z = -1`，要求变矮一步；
- 松键超过超时时间：前进和转向回零。

键盘只发归一化方向，实际最大速度、最大偏航角速度和每步身高由 `chassis` 参数决定。

### 5.2 `imu`：可选姿态解算节点，当前正常仿真没有启动

入口：`project/node/imu/imu.cpp`  
实现：`ros2_layer/node/imu/imu.hpp`

该节点订阅原始 `/imu`，通过通用 IMU 模块融合角速度和加速度，然后发布：

- `/imu/attitude`
- `/imu/quaternion`
- `/imu/euler_rad`
- `/imu/euler_deg`
- `/imu/angular_velocity`
- `/imu/linear_acceleration`

当前 Gazebo 的 `/imu.orientation` 可直接提供仿真姿态真值，所以 `chassis` 直接订阅 `/imu`，`sim.launch.py` 中的 `imu` 节点被注释掉。实车接入时，才需要明确把控制器切到融合后的姿态来源。

### 5.3 `leg`：旧腿姿保持器，已退出正常控制链

入口：`project/node/leg/leg.cpp`  
实现：`project/node/leg/leg.hpp`

这是阶段 2 使用的调试节点，功能是：

- 订阅四个腿关节反馈；
- 计算静态重力前馈；
- 使用关节 PD 把髋膝保持在固定目标角；
- 发布四路腿关节力矩。

现在腿力矩已经由 `chassis` 的全身 LQR 统一生成，所以正常 `sim.launch.py` 不再启动 `leg`。不能同时启动 `leg` 和当前 `chassis` 去发布同一组腿关节命令，否则两个控制器会争抢四条力矩话题。

## 6. 离线工具，不是运行时节点

### `generate_wheel_leg_lqr`

源码：`project/tools/generate_wheel_leg_lqr.cpp`

它不在实时控制链上。职责是：

1. 读取并展开当前轮腿 URDF；
2. 提取质量、惯量和腿几何；
3. 在指定身高建立 Pitch 共模和 Roll 差模模型；
4. 线性化得到 A/B；
5. 离散化并求解 LQR 增益 K；
6. 计算 X0/U0；
7. 执行 21 项模型与闭环检查；
8. 写入 `project/gains/wheel_leg/*.yaml`。

运行时 `chassis` 只读取生成结果，不会在线求解 Riccati 方程。

## 9. 为什么会卡在梯形障碍里

当前 LQR 的主要模型假设是“两轮都在地面、只有轮地接触”。进入梯形障碍后，可能增加底盘或腿杆接触、轮子失载、法向力重分配等约束，原模型不再成立。

此时现有控制器会这样反应：

1. 共模高度环继续追原来的 `target_height_m`；
2. Roll 环继续压制左右腿角差；
3. Pitch 环继续维持俯仰并尝试前进；
4. 碰撞约束使这些目标无法同时满足；
5. LQR 请求越来越大的髋膝力矩；
6. 力矩分配器按 `1.5 N·m` 上限裁剪，并可能触发软限位；
7. 机器人停在一个“没有倒下，但也无法脱离障碍”的受约束平衡点。

因此，Roll 已经工作不等于机器人会自动缩腿。自动缩腿属于共模身高规划；而且是否应该缩腿取决于接触状态：轮子仍着地时盲目缩腿会降低底盘净空，可能卡得更深。

## 10. 下一步合理的系统边界

如果目标是可靠越过当前梯形障碍，下一层应在 `chassis` 的 LQR 目标之上增加地形/动作监督器，而不是直接修改 Roll K：

1. 增加轮、腿杆或底盘接触信息；
2. 检测“有前进指令但位移很小、力矩持续饱和”的卡滞状态；
3. 区分轮子撞坡、底盘托底、腿杆接触和轮子失载；
4. 根据接触状态生成身高共模和左右差模轨迹；
5. 保留现有 LQR 作为轨迹附近的快速稳定内环；
6. 越障完成后平滑恢复正常身高和普通平衡模式。

这时职责应保持为：上层决定“腿要去哪里”，现有 `chassis` 内环决定“六个执行器此刻出多少力”。
